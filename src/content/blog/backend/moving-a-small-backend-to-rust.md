## Why Rust?

그동안 백엔드는 주로 Kotlin과 Spring Boot로 개발해 왔다. Spring은 여전히 편하고 익숙하다. 다만 서비스가 커질수록 빌드와 테스트를 기다리는 시간, 애플리케이션이 쓰는 메모리가 조금씩 더 신경 쓰이기 시작했다.

특히 AI와 함께 코드를 쓰면서 기다리는 시간이 더 눈에 들어왔다. 코드는 금방 나오는데, 그 코드가 제대로 동작하는지 확인하는 데는 여전히 시간이 걸렸다. AI가 작성한 테스트도 빠르게 늘었다. 기존 테스트를 정리하고 새 테스트를 작성하는 기준도 손봤는데, 계속 이런 식으로 대응하는 데에는 한계가 있다고 느꼈다.

GraalVM Native Image도 시도해 봤다. 시작 시간과 메모리 사용량을 줄일 수 있다는 점은 매력적이었다. 막상 해 보니 AOT 컴파일을 위해 기존 의존성과 초기화 설정을 하나씩 확인해야 했고, 빌드도 예상보다 훨씬 오래 걸렸다. 이미 빌드를 기다리는 게 부담스러워서 시작한 일인데, 더 긴 빌드를 기다리며 설정을 고치고 있으니 솔직히 흥미가 좀 떨어졌다.

그러다 문득 그냥 Rust가 생각났다.

사실 예전부터 배워 보고 싶었던 언어였다. 몇 번 들여다보긴 했지만 러닝 커브가 높아 늘 수박 겉핥기로 끝났다. 마침 일론 머스크의 글을 읽은 것도 다시 관심을 갖게 된 계기였다. 하드웨어와 AI를 좀 더 의식하면서 앱을 만들어 보고 싶다는 생각이 들었다.

예전과 달라진 게 있다면 이제는 AI와 함께 코드를 쓸 수 있다는 거다. Rust를 충분히 익힐 때까지 미뤄 두지 말고, 작은 서비스 하나를 직접 옮기면서 배워 봐도 되지 않을까?

그래서 한번 해 봤다.

## 먼저 작은 프로젝트부터

처음부터 큰 서비스를 옮길 자신은 없었다. 그래도 예제만 만들어 봐서는 내가 궁금한 걸 알기 어려울 것 같았다. 그래서 규모는 작지만 실제로 쓰고 있는 서비스 하나를 골랐다.

HTTP 서버는 axum, 데이터베이스 처리는 SQLx를 사용했다. 기존 PostgreSQL 데이터와 마이그레이션 이력은 그대로 이어받고, Flyway가 맡던 마이그레이션 실행도 SQLx로 옮겼다.

구현은 영역을 나눠 AI 에이전트에 맡겼다. 진행 상황은 파일 하나에 모아 뒀는데, ‘코드를 옮겼다’와 ‘기존 서버와 같은 결과가 나오는 걸 확인했다’를 따로 표시했다. 코드는 꽤 빨리 옮겨졌다. 시간이 걸린 건 두 번째 쪽이었다.

먼저 Kotlin 서버에 요청을 보내 상태 코드와 헤더, 응답 본문을 기록했다. 데이터를 바꾸는 요청은 DB에 어떤 값이 남는지도 확인했다. 그런 다음 Rust 서버에 같은 데이터와 요청을 넣고 결과를 비교했다. 로컬에서는 Kotlin이 쓴 데이터를 Rust가 읽고, 반대로 Rust가 쓴 데이터를 Kotlin이 읽는 것까지 해 봤다.

이 과정에서 평소에는 신경 쓰지 않던 차이가 꽤 나왔다. URL을 해석하는 방식도 조금씩 달랐고, 같은 값을 돌려줘도 JSON에 숫자가 찍히는 모양이 달랐다. Spring과 Tomcat이 그동안 알아서 해 주던 일이 생각보다 많았다. Rust 코드만 읽어 봤다면 어디를 맞춰야 하는지 몰랐을 것 같다.

## 실제로 달라진 것들

전환하고 나서 가장 먼저 체감한 건 기동 시간이었다. 서버가 뜨는 시간이 짧아졌고, 컨테이너 이미지도 많이 작아졌다. 요청이 거의 없는 시간대에는 메모리 사용량도 눈에 띄게 줄었다. 트래픽이 몰릴 때의 메모리는 뒤에서 한 번 더 이야기할 일이 있다.

개인적으로 가장 반가웠던 건 테스트였다. 컴파일을 마친 뒤에는 로컬에서 테스트 전체가 금방 끝났다. 대신 컴파일 자체는 전보다 오래 걸렸다. 코드를 고치고 결과를 보기까지 걸리는 시간을 생각하면 이 둘을 같이 봐야 한다.

PR을 올리고 검증 결과를 기다리는 시간도 짧아졌다. 다만 이번에 CI에서 수행하는 작업도 달라졌고, Kotlin과 Rust의 로컬 테스트를 같은 조건에서 재 보지도 못했다. 두 언어의 테스트 속도가 얼마나 차이 나는지는 이번 경험만으로 말하기 어렵다. 그래도 PR을 올리고 다른 일을 시작할까 말까 고민하는 시간은 줄어서 좋았다.

## 메모리는 한 번 더 손봤다

평소 메모리 사용량이 워낙 낮아서 처음에는 이 정도면 꽤 여유가 있겠다고 생각했다. 그런데 로컬에서 이미지 요청을 여러 건 겹쳐 보니 메모리 부족으로 서버가 종료됐다.

이미지를 처리하는 동안 같은 데이터가 메모리에 여러 벌 남아 있었고, 요청이 겹치면 그만큼 메모리를 더 썼다. 한 번에 처리하는 양을 제한하고, 처리 중에 커진 버퍼도 정리하도록 수정했다. 그러고 나서 같은 부하 시험을 다시 돌렸을 때는 끝까지 통과했다.

처음 궁금했던 건 ‘서버를 띄워 두면 메모리를 얼마나 쓰나’였다. 막상 옮겨 보니 ‘요청 하나를 처리하는 동안 메모리를 얼마나 쓰고, 그런 요청이 몇 개까지 겹칠 수 있나’도 같이 봐야 했다. Rust로 옮기고 나서도 이 부분은 내가 직접 챙겨야 했다.

## 다음에도 Rust를 쓸까?

개발 생산성까지 좋아졌냐고 묻는다면 아직 잘 모르겠다. 작은 서비스 하나를 옮겨 본 경험이고, 여러 사람이 오랫동안 기능을 추가하고 유지보수할 때 어떨지는 겪어 보지 못했다. 기동 시간과 메모리에서는 만족스러운 결과가 나왔지만, 컴파일을 기다리거나 Spring에서 당연하게 쓰던 동작을 직접 맞추는 데 들어간 시간도 있었다.

그래도 솔직히 나는 Spring보다 Rust를 더 배우고 싶다. 아니, 써 보고 싶다.

다음에는 조금 더 큰 서비스에서도 한 부분을 골라 옮겨 보고 싶다. 규모가 커져도 이번에 좋았던 점들이 그대로 남을지, 직접 챙겨야 하는 일이 얼마나 더 늘어날지 궁금하다.

일단 내가 언어를 고를 수 있는 새 프로젝트는 Rust로 시작해 보려고 한다. 그러다가 더 써 보고 싶은 언어가 나오면 또 옮기지 않을까?
