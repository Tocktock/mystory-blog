서버를 다른 언어로 다시 만든다고 하면 가장 먼저 드는 질문이 있습니다.

**굳이?**

기존 Kotlin·Spring Boot 서버도 정상적으로 동작하고 있었습니다. Rust로 옮긴다고 갑자기 사용자가 새로운 기능을 얻는 것도 아니죠. 오히려 그동안 프레임워크가 알아서 처리하던 것들을 다시 구현해야 하고, 잘못하면 이미 잘 돌아가던 기능까지 망가뜨릴 수 있습니다.

그럼에도 이번에는 운영 중이던 위키 백엔드 하나를 Rust로 완전히 옮겨보기로 했습니다. 목표는 명확했습니다. **기존 기능은 그대로 유지하되, JVM을 제거했을 때 운영 비용과 개발 과정이 실제로 어떻게 달라지는지 확인하는 것.**

2026년 11월 18일 설계 검토를 시작했고, 19일 밤 운영 전환을 마쳤습니다. 실제 전환 과정의 서비스 중단은 약 7분이었습니다.

## 성능보다 먼저 걱정했던 것

처음부터 가장 중요한 문제는 속도가 아니었습니다.

기존 API가 같은 입력에 같은 결과를 내놓는가? 로그인이나 문서 작성처럼 상태가 바뀌는 요청도 제대로 동작하는가? 오류 응답, 날짜, 직렬화 방식처럼 평소에는 눈에 띄지 않는 계약까지 지킬 수 있는가?

기존 Kotlin 코드를 보고 Rust로 다시 작성하는 것만으로는 부족했습니다. 코드를 해석한 사람이 원래 동작을 잘못 이해했을 수도 있으니까요.

그래서 **기존 서버의 실제 응답을 정답지로 삼는 방식**을 사용했습니다. Kotlin 서버를 실행해 응답을 기록하고, 같은 조건에서 Rust 서버가 어떤 결과를 내는지 비교하는 방식입니다.

전체 122개 HTTP 경로를 옮겼고, 그중 118개는 기존 서버의 실행 결과를 기록해 비교했습니다. 나머지 4개 헬스 경로는 별도로 이식 여부를 확인했습니다.

여기서 중요했던 건 테스트 개수가 아니었습니다. *테스트가 기존 서버와 새 서버의 차이를 정말 발견할 수 있느냐*였습니다.

## 정말 99%나 줄었을까?

운영 전후의 낮은 트래픽 구간을 비교한 결과는 꽤 인상적이었습니다.

| 항목 | Kotlin | Rust |
| --- | ---: | ---: |
| 태스크당 유휴 메모리 추정 | 약 480MiB | 약 3MiB |
| 태스크 기동 | 약 34초 | 약 3초 |
| 압축 컨테이너 이미지 | 336.9MB | 35.6MB |
| ECS 태스크 메모리 할당 | 2,048MiB | 512MiB |

유휴 메모리 지표로 계산한 감소율은 약 99%, 기동 시간은 약 92%, 이미지 크기는 약 89% 감소했습니다. ECS에 예약하던 태스크 메모리도 최종적으로 75% 줄였습니다.

물론 여기에는 조건이 붙습니다.

메모리 절대값은 CloudWatch 지표를 태스크 설정으로 환산한 **추정치**입니다. 비교 시간대의 요청 수도 적었고, Kotlin과 Rust에 들어온 요청의 종류도 같지 않았습니다. 따라서 이 숫자를 근거로 **Rust가 실제 트래픽 처리 성능에서 99% 더 좋다**고 이야기하면 안 됩니다.

또한 공용 EC2 인스턴스 수를 줄인 것은 아니기 때문에, 할당 메모리가 줄었다고 AWS 청구액까지 그만큼 줄었다는 뜻도 아닙니다.

그럼에도 유휴 리소스와 기동 비용이 눈에 띄게 줄었다는 점은 분명한 성과였습니다.

## 그런데 이미지 몇 개를 동시에 요청하니 죽었다

여기서 끝났다면 꽤 단순한 성공담이었을 겁니다.

문제는 메모리를 더 줄일 수 있겠다고 생각하고 이미지 요청을 동시에 넣어봤을 때 발생했습니다.

평소 서버가 메모리를 3MiB 정도만 쓴다고 해서, 메모리 상한을 그 수치에 맞춰 잡을 수는 없었습니다. 이미지 업로드와 조회 과정에서 같은 이미지가 여러 버퍼에 중복으로 올라가고, 요청이 끝나도 일부 메모리가 즉시 운영체제로 반환되지 않았기 때문입니다.

수정 전 구현은 512MiB 제한에서도 업로드 이후 이미지 조회를 24건 동시에 수행하는 조건에서 메모리 부족(OOM)으로 종료됐습니다.

원인을 좇아보니 단순히 Rust냐 Kotlin이냐의 문제가 아니었습니다.

이미지 업로드는 처리 중 여러 벌의 버퍼를 유지했고, 조회 요청에는 동시 처리 상한이 없었습니다. SQL 연결 버퍼와 메모리 할당기의 동작도 영향을 주고 있었습니다.

그래서 업로드와 조회가 공유하는 메모리 예산을 두고, 예산이 부족하면 요청을 무작정 실행하는 대신 기다리게 했습니다. 사용이 끝난 버퍼를 정리하는 부분도 수정했습니다.

수정 후 로컬 Docker 환경에서 업로드·조회 혼합 동시 요청을 포함한 테스트를 통과했고, 256MiB 제한에서 관측한 최대 사용량은 약 149MiB였습니다. 이후 운영 태스크 메모리는 512MiB로 설정했습니다.

단, 이 실험은 운영 트래픽 전체를 재현한 부하 테스트가 아니었습니다. 느린 클라이언트나 다른 종류의 쓰기 요청까지 충분히 검증했다고 볼 수는 없습니다.

**유휴 메모리가 적다는 것과, 부하 상황에서 안전하다는 것은 완전히 다른 이야기였습니다.**

## Rust로 바꾸면 개발도 빨라질까?

이 부분은 기대와 조금 달랐습니다.

Rust는 컴파일이 느렸습니다. 로컬의 같은 Docker Linux ARM64 환경에서 파일 하나를 수정한 뒤 테스트 코드를 다시 빌드할 때 Kotlin은 약 0.9초, Rust는 약 4.7초였습니다. 새로 빌드할 때도 Rust 쪽에 시간이 더 들었습니다.

그런데 GitHub Actions에서 PR 검사 결과를 받는 시간은 기존 약 4~6분에서 약 1~2분으로 줄었습니다. 배포 job의 중앙값도 약 386초에서 330초가 됐습니다.

모순처럼 보이지만 기준이 다릅니다. **컴파일 속도**는 느려졌지만, 테스트에 필요한 JVM 기동과 Testcontainers 의존성이 없어지고 CI 구성이 달라지면서 **전체 대기 시간**은 짧아진 겁니다.

그래서 언어를 비교할 때 단순히 '빌드가 빠르다/느리다'라고 결론 내리는 것도 조심해야겠다고 느꼈습니다. 개발자가 실제로 기다리는 시간은 컴파일러 하나만으로 결정되지 않으니까요.

## 바꾸면서 알게 된 것들

이번 작업에서 의외로 효과가 컸던 것은 새 언어 자체보다 이관 방법이었습니다.

첫째, **기존 동작을 먼저 기록하는 것.** 문서나 코드만으로 추측하는 대신, 실행되는 서비스를 기준으로 호환성을 확인할 수 있었습니다.

둘째, **배포 준비와 실제 전환을 분리하는 것.** 준비 작업이 끝났다는 사실과 운영 트래픽을 새 서버로 넘겨도 된다는 판단은 다릅니다. 실제 쓰기·로그인·주간 다이제스트 같은 기능은 운영 전환 뒤에도 별도로 확인했습니다.

셋째, **좋은 숫자가 나와도 최악의 조건을 보는 것.** 유휴 메모리가 극적으로 줄었다는 결과에 만족했다면 이미지 동시 요청의 문제를 놓쳤을 겁니다.

마지막으로, **Rust가 자동으로 문제를 해결해 주지는 않는다는 것.** JVM을 제거하면서 얻은 이점도 있었지만, 프레임워크가 숨겨주던 동작을 직접 책임져야 하는 부분도 늘어났습니다.

## 그럼 다른 서버도 전부 Rust로 옮길까?

아직은 아닙니다.

이번 사례에서는 작은 규모의 위키 백엔드를 통째로 옮겨 호환성 검증을 할 수 있었고, 유휴 리소스 측면에서도 꽤 큰 개선을 얻었습니다. 하지만 더 복잡하고 트래픽이 많은 서버라면 마이그레이션의 위험과 검증 비용부터 달라집니다.

기존 언어가 나쁘기 때문에 새로운 언어를 쓰는 것이 아니라, **무엇을 개선하려는지 명확하고 그 효과를 확인할 수 있을 때** 바꾸는 것이 맞다고 생각합니다.

이번에 가장 크게 배운 건 Rust 문법이 아니라 이거였습니다.

**서버를 다시 만드는 일보다, 이전과 똑같이 동작한다고 증명하는 일이 훨씬 중요하다.**

그리고 메모리 99%라는 예쁜 숫자보다, 이미지 요청 몇 건에 서버가 죽었던 순간이 오래 기억에 남을 것 같습니다.
